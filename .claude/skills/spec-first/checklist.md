# spec 완료 체크리스트

spec을 올리기 전에 모두 확인한다. 해당하지 않는 줄은 "해당 없음"과 이유를 적는다. 규칙 원본은 `.claude/docs/spec-guide.md`다.

## 매뉴얼

- [ ] 작업 중 받은 지적은 `spec-guide.md` · 이 스킬 · 이 체크리스트 중 원인이 된 곳에 반영했다

## 무엇을 쓸지

- [ ] 스킬의 표로 기능 spec · 설계 문서(새 모듈, 의존 방향, 네트워크 · 인증 · 저장소 방식, 빌드 · 배포) 중 필요한 것을 골랐다. 둘 다 필요하면 둘 다 썼다
- [ ] spec은 작업 PR의 첫 커밋으로 올리고, 설계 문서가 필요하면 합의 전에 구현하지 않았다

## 기능 spec

- [ ] 위치가 맞다: 업무 규칙 · API는 `Projects/Domain/<기능>Domain/.spec/`, 화면 동작은 `Projects/Feature/<기능>/.spec/`, 앱 흐름(Coordinator · 딥링크 · 푸시)은 `Projects/App/.spec/`
- [ ] 같은 기능 spec이 있으면 새로 만들지 않고 갱신했다. 파일 이름은 기능을 설명하는 kebab-case다
- [ ] frontmatter `spec` · `modules`와 개요 · 동작 규칙 · 엣지 케이스 · 제약/가정 · 작업 모듈 · 영향 범위 · 미해결 질문 · 변경 이력 절이 있다
- [ ] 동작 규칙은 "무엇이 참이어야 하는가"로 쓰였고, 규칙마다 입력과 기대 결과가 있어 테스트 하나로 확인할 수 있다
- [ ] 작업 모듈 · 영향 범위 · 미해결 질문을 이번 이슈 기준으로 새로 썼고, 변경 이력 맨 위에 `- #<이슈> 한 줄 요약`이 있다
- [ ] 확인하지 않은 내용은 `미해결 질문`에 두었고, 구현을 막는 질문만 사용자에게 물었다
- [ ] 구조는 Attendance_iOS의 같은 역할 파일과 대조해 적었다

## 설계 문서

- [ ] `spec-guide.md` 설계 문서 형식(날짜 · 이슈 · 상태 · 범위, 문제 · 목표 · 설계 · 결정 사항 · 검증 · 단계)을 따랐다
